# relay 定位论证与风险评估

**日期:** 2026-09-02
**性质:** 架构定位文档（非构建计划）
**上下文:** 针对"为何自研 relay 而非使用社区组合方案"的论证，含已确认的网络环境约束。

---

## 1. 结论摘要

relay 不是"可选方案之一"，而是在本项目的网络环境里**唯一可行**的文件交换 + 远程命令执行方案。它从根上为一个特定拓扑设计，而这个拓扑恰好否定了所有主流的社区替代方案。

## 2. 已确认的网络环境（决定性约束）

```
本机 macOS ──┐
             ├──> 中转 Linux（唯一交汇点）<── 远端 Windows（NAT 后）
  能出公网    │
```

| 端 | 约束 |
|---|---|
| 远端 Windows | **无公网访问**、NAT 后、**无管理员权限** |
| 中转 Linux | **无管理员权限**（非 root，仅能跑用户态进程） |
| 本机 macOS | 能出公网、能连中转 |
| 全网 | **网络隔离**，所有流量强制经中转这一个点（星型拓扑） |

这四条合起来，直接否定了社区三大类替代方案（详见 §4）。

## 3. relay 的核心机制（一句话 + 数据流）

**一个把「文件传输 + 透明命令转发 + 事件触发 + 运维通道」四件事，收进单个 Go 二进制 + 三端 WebSocket 的一体化工具。**

拓扑：本地 CLI ↔ 中转(transit) ↔ 远端 executor，全部主动向中转发起 WebSocket 连接。

| 能力 | 机制 |
|---|---|
| 文件传输 | push/pull，64KB 分块 + zstd 压缩 + WebSocket 二进制帧 + sha256 端到端校验 |
| 透明命令转发 | `relay exec` → 中转**只转发不执行** → 远端 executor 以 `sh -c` 执行 → stdout/stderr 流式回流 + 退出码回传 |
| 事件触发 | watch 远端目录 → fsnotify 事件 → glob 匹配 → 触发本地 exec 任务链（支持 `if:` 条件链） |
| 配置热加载 | 推一份统一 config.yaml 免重启生效（校验 + 备份 `.bak` + 原子写） |
| 运维通道 | `relay sync`（配置热加载）、`relay version -r`（跨机版本核验）、`server-remote`（受控自升级） |

**关键设计决策：中转服务器是纯透明转发 + 文件存储，绝不执行命令。**

## 4. 为什么社区方案在你的环境下都不可行

### 4.1 Tailscale / Nebula / ZeroTier（mesh VPN）— 被"远端无公网"直接否定

- **远端无公网** → Tailscale 无法工作。mesh VPN 依赖每端连向公网的协调服务器 + DERP 中继做打洞/协商，**远端连不上公网就加入不了 tailnet**。
- **模型冲突** → Tailscale 是"设备互相直达"，会把中转边缘化；你的架构是**强制星型、所有流量经中转**，物理上冲突。
- **无 admin** → 即使有公网，Windows 端也要管理员装服务，装不了。

### 4.2 frp / nps / ngrok（NAT 穿透隧道）— 只解决连通性，不解决语义

- 它们只把 executor 的端口暴露到公网，**文件触发、命令转发语义全都要在之上再叠 ssh/scp**。
- 且需要远端/中转有相应客户端 + 出网能力，仍受"远端无公网"约束。

### 4.3 ssh ProxyJump / Fabric / Ansible — 被"无 sshd + 无公网 IP"否定

- ssh 的 `-J` 跳板模型与 relay"中转不执行命令"同构，但**前提是每端有 sshd + 公网可达**。
- 你的环境无公网、无 admin 装 sshd，ssh 链路搭不起来。

### 4.4 Syncthing + stfed（文件同步 + 触发）— 无命令转发回流、需装多 agent

- 只做"收文件→执行"，没有反向 CLI 命令流式回流；每端要装 Syncthing + 钩子 agent。

## 5. relay 的差异化价值（真正成立的锚点）

> **relay 的价值不在「连通性」，而在「工作流语义 + 受控通道」——而连通性恰是你的环境里所有社区方案都无法提供的。**

1. **三端主动连中转**：没有任何一端需要"主动出网"或"拥有网卡权限"。远端无公网没关系，它只要认得出中转地址、能建立出站连接即可——这是无公网环境下唯一能穿透的姿势。
2. **中转纯转发不执行**：中转是唯一交汇点，把它设计成"只搬数据、不落地执行"，正好匹配"无 admin、只跑用户态进程"的约束。
3. **命令级鉴权**：按 watch、按命令、按 token 的精细通道，而非"设备入网即全局互通"的粗粒度信任。
4. **热配置 + 状态核验**：`sync` 免重启推配置、`version -r` 跨机核验，是社区拼装方案没有的运维闭环。
5. **受控自升级通道**：正因为中转无 admin 且 ssh 不可达，才需要 `server-remote` 这条"用户态自替换二进制"的窄径来升级唯一交汇点——这不是花哨，是无管理员前提下升级中转的唯一办法。

## 6. 剩余风险（网络约束下剩下的）

| 风险 | 等级 | 说明 | 缓解 |
|---|---|---|---|
| 自升级通道安全边界 | 中 | token 持有者可替换并重启中转二进制，是"任意代码执行 + 持久化"级权限 | 发布侧加**签名**（当前仅 sha256 完整性，无真实性）；文档已注明"可选" |
| 可靠性边界 | 低-中 | 乱序块按 offset 丢弃、重连不续传在途流、幂等只靠路径去重——单连接内可靠，非跨重连 exactly-once | 当前规模可接受；未来 GB 级传输需补断点续传 |
| 生态归零 / 单点协议 | 中 | 自研 WS 协议 + 单作者工程，升级只能靠自己 | 保持 MCP backend 标准兼容通道（fs-mcp/relay backend），留标准后路 |

## 7. 结论

relay 的存在是**必要且正当**的：它为一个"远端无公网 + 三端无 admin + 强制经中转"的环境从根上设计，而这个环境否决了所有主流社区替代。剩下的工作不是"要不要自研"，而是"如何把自研做稳"——优先级：

1. 给自升级通道加签名（当前唯一的"任意代码执行"级风险）。
2. 补断点续传（为 GB 级文件传输铺路，当前可延后）。
3. 保持 MCP 标准兼容作为生态后路。
